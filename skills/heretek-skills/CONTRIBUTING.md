# Contributing to Heretek Skills

Thanks for adding a skill! This guide covers the format, naming, and validation expectations.

## Folder layout

Every skill lives in its own folder under `skills/`:

```
skills/
├── <skill-name>/
│   ├── SKILL.md            # Required. Entry point + metadata.
│   ├── references/         # Optional. Distilled docs loaded on demand.
│   ├── scripts/            # Optional. Helper shell/Python scripts.
│   └── assets/             # Optional. Templates, images, fixtures.
├── _template/              # Blank starter. Copy this to add a new skill.
├── .gitkeep
└── ...
```

Keep each skill **flat** under `skills/<skill-name>/`. Do not nest skill folders.

## How to add a new skill

1. **Copy the template:**
   ```bash
   cp -r skills/_template skills/<your-skill-name>
   ```

2. **Edit `SKILL.md`** — fill in the YAML frontmatter and body sections.

3. **Validate locally:**
   ```bash
   npx -y skills-ref validate skills/<your-skill-name>
   ```

4. **Open a PR.** The CI workflow (`.github/workflows/validate-skills.yml`) will run `skills-ref validate` and `skills-ref readme` and check for naming drift.

## Required frontmatter

Each `SKILL.md` must begin with a YAML block delimited by `---`:

```yaml
---
name: <skill-name>            # Required. See "Naming rules" below.
description: <one-paragraph>  # Required. See "Description rules" below.
---
```

### Naming rules

- `name` must **exactly match** the parent directory (e.g., folder `foo-bar/` → `name: foo-bar`).
- Lowercase letters, digits, and hyphens only.
- Max 64 characters.
- Cannot start or end with a hyphen; cannot contain `--`.

### Description rules

- Max 1024 characters.
- Must describe **what the skill does** AND **when to use it**.
- Include trigger phrases users will say. Examples: _"create a morphe patch"_, _"add a patch to my morphe bundle"_, _"remove ads from X"_, _"fingerprint and patch method Y"_.
- **All "when to use" info lives in the description**, not in the body. The body is loaded only after the skill is activated, so a thin description means the skill won't trigger.
- Be **pushy** — describe the symptoms the user might describe, not just the formal name. Common user phrasings like "I want to…", "how do I…", "add a…", "make X Y" should appear if natural.

## Body sections (recommended)

Body is freeform, but most skills follow this structure:

```markdown
## When to use
## Inputs required
## Workflow
## Reference index
## Common pitfalls
## Minimal worked example
```

Keep the body under **500 lines**. Anything longer should be split into `references/*.md` and linked with relative paths.

## Progressive disclosure

Files are loaded lazily:

1. **At startup** (~100 tokens): frontmatter (`name`, `description`) only.
2. **On activation** (≤ 5000 tokens): the full `SKILL.md` body.
3. **On demand** (unlimited): referenced files in `references/`, `scripts/`, `assets/`.

Use this to your advantage: keep `SKILL.md` focused on the workflow, and put deep-dives in `references/`.

## Scripts

- Place in `scripts/`. Name with `kebab-case.sh` or `kebab-case.py`.
- Start with `#!/usr/bin/env bash` (or `#!/usr/bin/env python3`) and `set -euo pipefail` for shell scripts.
- Wrap long-running operations with clear error messages.
- Document inputs and outputs in the script's top-of-file comment.

## Anti-patterns

- ❌ **No copy-pasted upstream docs.** Distill and rephrase content from third-party sources. The MIT license on this repo does not cover verbatim copies of GPLv3+ sources.
- ❌ **No reused Morphe branding in derivative bundle names or logos.** Section 7 of the upstream GPLv3 prohibits this — the skill itself is fine, but artifacts you produce must respect the upstream branding rules.
- ❌ **No hand-edited generated files.** If you reference `patches-list.json`, `patches-bundle.json`, or `CHANGELOG.md`, note that they are regenerated by Gradle; instruct the contributor to run the generator instead of editing them.
- ❌ **No underscore-prefixed skill names.** The `_template` is the only exception; it is intentionally skipped by registries.
- ❌ **No two skills with the same `description` semantics.** If you find a duplicate, fold it into the existing skill or split the existing skill first.

## Validation

The CI workflow runs `skills-ref validate` on every PR touching `skills/**`. Locally:

```bash
npx -y skills-ref validate skills/<skill-name>
```

This checks frontmatter constraints, name/directory match, and a few common mistakes.

## Releasing

The repo follows [Conventional Commits](https://www.conventionalcommits.org/) for clarity. Each merged PR that adds a skill should result in a README entry (auto-generated by `npx skills-ref readme`).
