# Cumulative codebase-staleness metric

> Phase: 4. Type: spike. Ideation approach: external-data.
> Filed: 2026-08-06. Sources verified: 2026-08-06.

## Background

Per-edit staleness (#36, #37, #40, #43, #45) catches fresh emissions. The cumulative question — "across the whole codebase, how stale are we on average, and how is that trending?" — has no answer in heretek today. This spike builds a codebase-wide metric that aggregates per-issue staleness into a single trendable number, feeding into the security-monitoring pipeline's reporting and the eventual M24 roadmap roll-up (#50–53).

## Research Summary

- Cross-cutting observation #1 from the research report: stale training data is the dominant failure mode, which motivates tracking cumulative staleness ([research report](docs/superpowers/research/2026-08-06-freshness-enforced-coding-research.md), verified 2026-08-06).
- Propelcode's summary of CodeRabbit's analysis reports 89% GPT-5 suggestion accuracy, 75% self-detection, and 20% slopsquatting; use these as general measurement context, not as evidence of a six-month cumulative trend ([propelcode](https://www.propelcode.ai/blog/emergent-code-review-patterns-ai-generated-code), verified 2026-08-06) — methodology reference.
- arXiv 2406.09834 studies deprecated-API use across 7 LLMs and 8 Python libraries in a single language (Python); it provides a cross-sectional measurement corpus, not a longitudinal per-codebase metric ([arxiv](https://arxiv.org/html/2406.09834v1), verified 2026-08-06) — metric-definition context.

## Ideation Notes

*external-data triangulation.* Three independent inputs triangulated: (a) the research report's stale-data observation; (b) Propelcode's accuracy, self-detection, and slopsquatting figures as measurement context; (c) arXiv 2406.09834's 7-LLM/8-Python-library cross-sectional corpus. Combined with the security-monitoring pipeline's existing per-issue reporting, these inputs motivate a roll-up metric that aggregates per-issue staleness scores (from #36 freshness + #40 forbidden patterns) into a single trendable codebase-level number. Novel in heretek because it bridges per-edit freshness (Phase 1–3) with roadmap-level reporting (#50–53 long-term tests).

## Scope

- Metric: `cumulative_staleness_score` per codebase, defined as the freshness-cache-weighted count of stale patterns + forbidden-pattern matches + missing freshness tokens (#46).
- Script `scripts/cumulative_staleness.py` that scans a repo and emits the score + per-file breakdown.
- Trendable: the score is a function of (snapshot_date, codebase), so a series over time is meaningful.
- Integration with the security-monitoring pipeline's reporting output.

## Out of scope

- Auto-remediation based on the score (this is measurement-only).
- Cross-codebase comparison (per-codebase first; cross-codebase is a follow-up).
- LLM-judged staleness augmentation (rule-based only in this spike).

## Hypothesis + method

**Hypothesis:** A cumulative codebase-staleness metric — aggregating per-issue freshness-cache deltas + forbidden-pattern matches + missing freshness tokens — correlates ≥0.5 with the eventual task-success-rate regression observed when running the same task set against the codebase over time.

**Method:**
1. Define `cumulative_staleness_score` precisely (formula in `docs/superpowers/research/2026-08-06-cumulative-staleness-definition.md`).
2. Implement `scripts/cumulative_staleness.py`.
3. Run on heretek's own codebase + 5 sample projects; record baseline scores.
4. Run task set on each codebase monthly for 6 months; record task-success-rate regression.
5. Compute correlation between baseline staleness score and 6-month task-success-rate regression.

**Success criteria:**
- Correlation ≥0.5 (Pearson).
- Score is stable across re-runs (idempotent).
- Per-codebase scan <30s for 10k LoC codebases.

**Decision deliverable:** ADR-style note recommending either (a) ship the metric + integrate with security-monitoring pipeline reporting, (b) refine the formula (e.g., add LLM-judged component), or (c) the metric is too noisy to be useful — abandon.
