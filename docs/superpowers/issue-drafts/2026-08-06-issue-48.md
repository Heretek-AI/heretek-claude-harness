# SVoK / provenance comments research

> Phase: 4. Type: spike. Ideation approach: cross-domain.
> Filed: 2026-08-06. Sources verified: 2026-08-06.

## Background

"Source-Verified-on-Knowledge" (SVoK) comments are a richer form of freshness tokens (#46): instead of just recording the freshness-cache snapshot date, they record *which external source* verified the code, what version of that source, and when. Borrowed from academic citation discipline and adapted to code. The spike investigates whether this richer provenance is worth the per-edit overhead and reader cognitive load.

## Ideation Notes

*cross-domain transfer.* Borrowed from academic citation and software-archaeology literature. Academic citation discipline handles exactly this problem: a claim is followed by the source, the version, the access date. The transfer applies that discipline to emitted code: every non-trivial code block carries the sources backing it. Novel in heretek because freshness tokens (#46) record the *cache snapshot*, while SVoK records the *direct source* — a richer provenance that survives even when the cache is regenerated.

## Scope

- Design SVoK comment format: `# heretek-svok: lib=requests ver=2.32.3 src=context7 fetched=2026-08-06`.
- Prototype `scripts/svok_emit.py` that takes a code block + a Context7 (or similar) lookup result and emits the SVoK comment.
- Reader-mode `scripts/svok_read.py` that parses SVoK comments and surfaces the provenance on demand (e.g., for code review).
- Test bench: 30 code blocks spanning 3 ecosystems, with realistic SVoK coverage.

## Out of scope

- Auto-SVoK (model decides when to stamp; deferred).
- SVoK verification (does the cited source actually contain the cited API?) — orthogonal.
- Cross-source consistency checks (multiple sources backing one block).

## Hypothesis + method

**Hypothesis:** SVoK comments — recording the direct external source backing each emitted code block, plus the source's version and fetch date — measurably improve downstream code-review accuracy (≥20% fewer "is this still current?" questions) without exceeding a 2× comment-density overhead.

**Method:**
1. Implement `scripts/svok_emit.py` and `scripts/svok_read.py`.
2. Curate 30 code blocks: 10 with rich SVoK, 10 with bare freshness tokens (#46), 10 with no provenance.
3. Run a controlled review task with N=10 reviewers; measure review-question count, review accuracy, time-to-review.
4. Compare SVoK-equipped vs freshness-token-only vs bare code.

**Success criteria:**
- SVoK reduces "is this still current?" review questions by ≥20% relative to bare code.
- SVoK outperforms bare freshness tokens (#46) on the same metric by ≥10% (the "richer is worth it" question).
- Comment density overhead ≤2× bare code.

**Decision deliverable:** ADR-style note recommending either (a) ship SVoK as a richer alternative to #46 tokens, (b) tokens are enough — SVoK too heavy, or (c) the abstraction isn't worth pursuing.
