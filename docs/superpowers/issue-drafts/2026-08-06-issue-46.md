# Freshness tokens system (`scripts/freshness_tokens.py`)

> Phase: 3. Type: ship. Ideation approach: external-data.
> Filed: 2026-08-06. Sources verified: 2026-08-06.

## Background

The freshness index (#36) tells *heretek* what's current. It doesn't tell *future readers of a code block* when the code was verified-against-what-state. Freshness tokens are machine-readable provenance markers embedded in code comments (or docstrings) that record: "this block was verified-against freshness-cache snapshot YYYY-MM-DD for libraries X, Y, Z." They enable the Phase 4 ideas (SVoK comments #48, counterfactual diffs #47) and let humans audit staleness at the file level.

## Research Summary

- InfoQ "Refreshing stale code intelligence" (QCon London 2026): documents the broader trend of provenance embedding in code — freshness tokens fit this category ([InfoQ](https://www.infoq.com/news/2026/03/stale-code-intelligence/), verified 2026-08-06).
- techbuzz: Google Gemini Docs MCP's Agent Skills include provenance-style "when-fetched" markers in tool responses ([techbuzz](https://techbuzz.ai/articles/google-fixes-ai-coding-agents-outdated-code-problem), verified 2026-08-06).
- Cross-cutting observation #4 from the research report: external-data triangulation works when the external state is *attached* to the artifact, not just consulted ([research report](docs/superpowers/research/2026-08-06-freshness-enforced-coding-research.md), verified 2026-08-06).

## Ideation Notes

*external-data triangulation.* Three independent observations triangulated: (a) InfoQ's coverage of provenance embedding in code; (b) Gemini Docs MCP's per-tool-response "when-fetched" markers; (c) the Phase 4 SVoK spike (#48) needs a substrate of provenance tokens. Synthesized as a heretek CLI (`scripts/freshness_tokens.py`) that emits `# heretek-freshness: snapshot=YYYY-MM-DD libs=[...]` markers, plus a CI check that flags comments older than the freshness cache. Novel because freshness tokens survive across the codebase — they're the only mechanism in this spec whose value compounds over time.

## Scope

- CLI `scripts/freshness_tokens.py` with subcommands: `stamp`, `verify`, `audit`.
- `stamp`: insert a freshness token comment into a file (or block) recording current freshness-cache snapshot + relevant lib list.
- `verify`: read tokens in a file and flag a token as stale iff its `snapshot_date` is older than the `snapshot_date` in the freshness-cache file for **any** listed library. `latest_release_date` remains informational and is not used as the comparison date. If a listed cache file lacks `snapshot_date`, report the token as unverifiable rather than guessing.
- `audit`: project-wide report — count tokens, list files with stale tokens, list files with no tokens.
- Integration with the freshness index (#36) for snapshot reference.

## Out of scope

- LLM-judged verification of token accuracy (orthogonal; #45 lookup-gate handles per-edit freshness).
- Auto-token-insertion during agent runs (the model decides what to stamp; deferred to #48 SVoK).
- Multi-language token formats beyond Python/JS/Rust (defer to Phase 4).
