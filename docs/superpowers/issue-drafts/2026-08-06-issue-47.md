# Counterfactual diffs prototype

> Phase: 4. Type: spike. Ideation approach: cross-domain.
> Filed: 2026-08-06. Sources verified: 2026-08-06.

## Background

When the freshness index (#36) and forbidden-pattern registry (#40) detect a stale pattern, the natural next question is "what would the current pattern look like?" Counterfactual diffs: a tool that, given a code edit, computes "if this had been written today with current library state, what would it look like?" — enabling reviewers to see the gap between emitted code and current best practice. Pure research: no current heretek substrate consumes this; the spike validates whether the abstraction is useful.

## Research Summary

- Cross-cutting observation #2 from the research report: external-data triangulation works, and counterfactual computation is one of its most powerful forms ([research report](https://docs.bswen.com/blog/2026-03-17-prevent-ai-hallucinations-outdated-docs/), verified 2026-08-06).
- Related cross-domain signal: counterfactual reasoning has been productized in adjacent spaces (causal inference in observability, what-if analysis in database query planners). The transfer to code freshness is novel.

## Ideation Notes

*cross-domain transfer.* Borrowed from causal-inference and counterfactual-reasoning literature. The transfer is non-trivial: counterfactual diffs require (a) a model of "what current state means" (provided by #36 + #40), (b) a diff operation parameterized by that state, (c) a way to compute the diff without actually applying it (read-only). Novel because no existing tool combines freshness caches with counterfactual reasoning — the abstraction is novel even if the underlying techniques are not.

## Scope

- Prototype `scripts/counterfactual_diff.py` taking a code block + library context, returning "what would this look like if written against current state."
- Implementation: rule-based for known patterns (from #40); LLM-assisted fallback for novel patterns.
- Test bench: 20 sample edits where the emitted form differs from the current form; manual review of generated counterfactual diffs.
- Output format: unified diff between "as emitted" and "current best practice."

## Out of scope

- Auto-applying counterfactual suggestions (read-only prototype only).
- Polyglot beyond Python (defer until prototype validates).
- Integration with the freshness tokens (#46) — orthogonal, could be a follow-up.

## Hypothesis + method

**Hypothesis:** A counterfactual-diff tool, given an emitted code block + freshness cache + forbidden-pattern registry, produces a useful diff to current best practice in ≥70% of cases (where "useful" = a human reviewer rates the diff as actionable, on a 1–5 scale ≥4).

**Method:**
1. Implement `scripts/counterfactual_diff.py` with rule-based path + LLM fallback.
2. Curate 20 sample edits: 10 with simple stale patterns (e.g., deprecated stdlib), 10 with subtle staleness (e.g., API drift in a third-party lib).
3. Generate counterfactual diffs for each.
4. Have 3 human reviewers rate each diff (1–5 actionable scale).
5. Compute: per-edit rating, inter-reviewer agreement, fraction rated ≥4.

**Success criteria:**
- ≥70% of generated diffs rated ≥4 by majority of reviewers.
- Inter-reviewer agreement ≥0.6 (Krippendorff's alpha).
- Wall-clock per edit <5s (rule-based path) / <30s (LLM fallback).

**Decision deliverable:** ADR-style note recommending either (a) ship as a research artifact + integration with future tools, (b) refine prototype, or (c) the abstraction isn't useful in this context — abandon.
