# Freshness eval harness (`tests/freshness_eval/`)

> Phase: 1. Type: ship. Ideation approach: external-data.
> Filed: 2026-08-06. Sources verified: 2026-08-06.

## Background

The freshness index (#66) and stale-dep intercept (#67) ship without a way to measure whether they actually reduce stale-output rate across model classes. Without measurement, "is this working?" reduces to vibes. This item is the harness that turns the foundation into something we can A/B test.

## Research Summary

- InfoQ coverage of QCon London 2026: "Refreshing stale code intelligence" frames the eval problem as a first-class concern, not a CI afterthought ([InfoQ](https://www.infoq.com/news/2026/03/stale-code-intelligence/), verified 2026-08-06).
- Propelcode's summary of CodeRabbit's analysis reports 89% GPT-5 suggestion accuracy, 75% self-detection, and 20% slopsquatting ([propelcode](https://www.propelcode.ai/blog/emergent-code-review-patterns-ai-generated-code), verified 2026-08-06) — concrete baselines for the eval harness.
- Cross-cutting observation #2 from the research report: "external-data triangulation works" — measuring edit outcomes against an external ground-truth (the freshness cache) is the only credible methodology ([research report](docs/superpowers/research/2026-08-06-freshness-enforced-coding-research.md), verified 2026-08-06).

## Ideation Notes

*external-data triangulation.* Synthesized from: (a) the freshness index (#66) provides a queryable external ground-truth; (b) the stale-dep intercept (#67) provides a measurable intervention; (c) the cross-cutting observation that all successful freshness mitigations are measured against external state. Combined as a pytest harness that runs N coding tasks against M model classes, with the freshness cache as oracle. Novel because the harness treats "cache freshness score" as a first-class metric alongside traditional accuracy/issue-rate.

## Scope

- `tests/freshness_eval/` with at least 30 representative tasks (10 per ecosystem: Python, JS, Rust).
- Each task seeds a repo with a stale dep pin; the model is prompted to fix it.
- Measurement: stale-version-pick rate, fix-cycle count, cache-hit rate, wall-clock per task.
- Runs against at least 2 model classes (e.g., Qwen3.6 27B + deepseek-class).
- CI integration via `.github/workflows/freshness-eval.yml` with opt-in `INTEGRATION` marker to control budget.

## Out of scope

- Live-model API integration in CI (uses cached model outputs from a separate run).
- Coverage of npm registry freshness drift (covered by #66's catalog refresh).
- Eval of forbidden-pattern registry (#70) — separate harness if needed.

## D5 / D7 implications

- **D5:** tests-only, not a plugin. No overlap with existing plugins.
- **D7:** no external runtime deps beyond pytest (already vetted).
- **D11:** N/A — eval harness is a test artifact.
- **CI budget:** 5–10 min per CI run, opt-in via `INTEGRATION` marker (per spec §9 Q3).

## Suggested catalog.yaml entry shape

Eval harness is not a plugin — it lives at `tests/`. No catalog entry required. Wire into CI via workflow file.

```yaml
# .github/workflows/freshness-eval.yml (sketch)
name: freshness-eval
on:
  workflow_dispatch:
  schedule:
    - cron: '0 6 * * 1'  # weekly
jobs:
  eval:
    if: contains(github.event.head_commit.message, '[INTEGRATION]') || github.event_name == 'schedule'
    runs-on: ubuntu-latest
    timeout-minutes: 10
```
