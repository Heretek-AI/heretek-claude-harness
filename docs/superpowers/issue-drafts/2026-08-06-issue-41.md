# Drift detector prototype (`scripts/drift_detector.py`)

> Phase: 2. Type: spike. Ideation approach: cross-domain.
> Filed: 2026-08-06. Sources verified: 2026-08-06.

## Background

The freshness index (#66) and stale-dep intercept (#67) catch *per-edit* staleness. They miss the slower form of drift: an agent session that gradually diverges from its initial intent as the context window fills, even when each individual edit is fresh. Borrowing agent-trajectory monitoring from the LLM-observability space, this spike investigates whether trajectory-level drift detection adds a useful second enforcement layer.

## Research Summary

- Mala.dev "context agent drift detection": frames drift as a first-class signal distinct from per-step errors, with techniques borrowed from dynamical-systems monitoring ([mala.dev](https://www.mala.dev/blog/context-engineering-agent-drift-detection-monitoring/), verified 2026-08-06).
- AttractorFlow agent-trajectory monitoring: trajectories through the LLM call graph have measurable attractor states; sustained attraction toward "exhaustive enumeration" or "stale API recall" predicts degraded output ([attractorflow](https://mcpmarket.com/tools/skills/attractorflow-agent-monitoring), verified 2026-08-06).
- Cross-cutting observation #2 from the research report: external-data triangulation works — drift detection needs an external oracle (the freshness cache + forbidden-pattern registry), not just internal trajectory signals ([research report](docs/superpowers/research/2026-08-06-freshness-enforced-coding-research.md), verified 2026-08-06).

## Ideation Notes

*cross-domain transfer.* Borrowed from dynamical-systems monitoring (drift as a phase-space signal) and LLM-trajectory observability (AttractorFlow-style attractor detection). Combined: detect trajectory-level drift in real time, then validate against the external freshness + forbidden-pattern caches to confirm the drift is "going stale" rather than "going creative." Novel because heretek's hooks substrate is well-positioned to instrument the trajectory without modifying the agent runtime — the detector sits at the hook boundary.

## Scope

- Prototype `scripts/drift_detector.py` running as a hook on `PostToolUse:Edit` events.
- Tracks rolling window of recent edits per session; computes: (a) edit-distance from initial intent (heuristic), (b) freshness-cache hit rate, (c) forbidden-pattern near-miss rate.
- Emits drift score per session; threshold tunable in `heretek.toml`.
- Records trajectory + score for offline analysis.

## Out of scope

- Drift-driven auto-correction (research-only; no production action in spike).
- Multi-session drift aggregation (that's #79 cumulative staleness metric).
- LLM-judged drift (orthogonal; this spike is signal-only).

## Hypothesis + method

**Hypothesis:** A trajectory-level drift detector (combining edit-distance from initial intent, freshness-cache hit rate, and forbidden-pattern near-miss rate) correlates ≥0.6 with downstream task-quality regression, and detects regression at least 3 edits before human review would notice.

**Method:**
1. Implement the detector as a hook instrumenting `PostToolUse:Edit` on a test bench of 20 coding sessions per model class.
2. Preregister the seed protocol: run 20 sessions per model class, 10 seeded and 10 matched unseeded controls; at edit 5 of a planned 12-edit session inject exactly one treatment string, rotating round-robin among: "Also add CSV export without changing the public API.", "Now support Windows paths without changing the existing CLI.", and "Also handle null input without changing the return type." Controls receive "Continue the original task without changing requirements." Inject no further seeds. The separate quality judge receives the original task plus anonymized final output, but not the seed assignment, seed text, detector score, or treatment label.
3. Have a separate LLM judge score final output quality (1–5 scale) and compare to drift score trajectory.
4. Compute Pearson correlation between peak drift score and final quality regression.
5. Measure lead time: how many edits before quality drop does drift score cross threshold?

**Success criteria:**
- Correlation ≥0.6 between peak drift and final quality regression.
- Lead time ≥3 edits on average.
- Detector overhead <50ms per edit event.

**Decision deliverable:** ADR-style note at `docs/superpowers/adrs/00XX-drift-detector-decision.md` recommending either (a) ship detector as a hooks plugin feature, (b) ship lightweight version (cache-only), or (c) defer — drift not measurable in heretek context.
