# Heretek Maintenance Skills Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Implement 3 heretek-claude-harness maintenance skills (`/heretek:catalog`, `/heretek:refresh-pins`, `/heretek:merge-and-push`) under `.claude/skills/` and mirror to `.agents/skills/`.

**Architecture:** Each skill is a `SKILL.md` file (the Skill tool loads it on invocation) under a directory. Two of the three skills are thin bash wrappers; the catalog skill is the heaviest and gets a mock-mode smoke test. Skills live under `.claude/skills/` (Claude Code) and `.agents/skills/` (opencode) — same content, separate paths because the two CLIs read different locations.

**Tech Stack:** Markdown (SKILL.md bodies), bash (wrapper scripts), Python 3 (existing `scripts/refresh_pins.py` and `scripts/validate.py`).

## Global Constraints

These apply to every task. Copy values verbatim from the spec:

- **License:** MIT for all new files (D14). The catalog skill references the marketplace's MIT-licensed code.
- **D11 SHA-ride:** no `version` field anywhere. The skill files reference git SHAs, not semantic versions.
- **D15 strict hooks ownership:** none of the skills modify plugin manifests or content files that could break the D15 invariant. If the catalog skill ever adds hook items, it routes them to the `hooks` plugin only.
- **All files end with trailing `\n`.** Every `SKILL.md` and test file written by any task must end with `\n`.
- **Conventional commits** for all skill-creation commits (`feat(skills): ...`, `test(skills): ...`, `docs(skills): ...`).
- **Skill file format:** every `SKILL.md` uses the standard Skill tool format — frontmatter with `description` field + body with steps. No exceptions.
- **D7 vetting bar (for catalog skill's research phase):** stars ≥ 500, last commit ≤ 12mo, OSI license, source-audit pass, no critical CVEs in 24 months.
- **Skill directories mirror exactly:** `.claude/skills/<skill>/SKILL.md` content must be byte-identical to `.agents/skills/<skill>/SKILL.md`. Mirror is enforced by Task 5.

```markdown

description: Add a vetted third-party item to heretek catalog (add-item mode) or scaffold a new plugin with its first items (add-plugin mode). Performs D7 vetting research, writes an ADR, updates catalog.yaml, and creates content files.
---

# /heretek:catalog

Add a new vetted item to an existing plugin's `items[]`, or scaffold a brand-new plugin with its first items. Always performs real research via the GitHub API and writes a real ADR — never use placeholder data.

## When to use

- A maintainer has researched a third-party candidate (rust-analyzer, ruff, biome, context7, etc.) and wants to ship it under the heretek marketplace.
- A new plugin category needs a first vetted item.
- A previously-rejected item's upstream has improved (stars grew, license added, etc.) and needs re-evaluation.

## Modes

This skill has two modes. If invoked without a subcommand, prompt the user:

> "Two modes: `add-item` (add a vetted third-party item to an existing plugin) or `add-plugin` (scaffold a new plugin with its first vetted items). Which mode?"

The user may also describe what they want and the skill should infer the mode.

## Steps (both modes)

### Step 1: Research

For each candidate item, run real research via the GitHub API. Do NOT use placeholder data.

```bash
gh api repos/{owner}/{repo} --jq '{stars: .stargazers_count, pushed: .pushed_at, license: .license.spdx_id}'
gh api repos/{owner}/{repo}/security-advisories --jq '[.[] | select(.severity == "CRITICAL")]'
```

Apply the D7 vetting bar (per `docs/superpowers/specs/2026-08-03-heretek-marketplace-design.md` §7):
- stars ≥ 500 → PASS or fail
- last_commit (from pushed_at) ≤ 12 months → PASS or fail
- license is OSI-approved (MIT / Apache-2.0 / BSD / etc.) → PASS or fail
- source-audit pass for code-executing components — human review documented in ADR
- 0 critical CVEs (CVSS ≥ 9.0) in 24 months → PASS or fail

If any D7 criterion fails, mark the item `rejected` in catalog.yaml and stop.

### Step 2: Write ADR

Write `catalog/reviews/<plugin>-<item>.md` using the template at `catalog/reviews/0000-template.md`. Fill in real research data — no placeholders.

### Step 3: Update catalog.yaml

**add-item mode**: append to existing plugin's `items[]`:
```yaml
- id: <item-slug>
  kind: skill | mcp | lsp | agent | output-style
  upstream: <owner>/<repo>
  sha: "<40-char-hex>"
  license: MIT
  vetting:
    status: approved
    date: <today>
    stars: <int>
    last_commit: <date>
    cve_scan: <today>
    review: reviews/<plugin>-<item>.md
```

**add-plugin mode**: add a new top-level plugin entry with `components: [...]` and `items: [...]`.

### Step 4: Write content files

**add-item mode**: based on `kind`, write the matching content file in the target plugin's directory:
- `kind: skill` → `plugins/<plugin>/skills/<name>/SKILL.md`
- `kind: mcp` → `plugins/<plugin>/.mcp.json` (or per-server `plugins/<plugin>/mcp/<name>/.mcp.json`)
- `kind: lsp` → `plugins/<plugin>/.lsp.json`
- `kind: agent` → `plugins/<plugin>/agents/<name>.md`
- `kind: output-style` → `plugins/<plugin>/output-styles/<name>.md`

**add-plugin mode**: scaffold the new plugin directory tree (`plugins/<plugin>/.claude-plugin/plugin.json` + first content files).

### Step 5: Update plugin README

Update `plugins/<plugin>/README.md` install + usage section. Per-plugin README documents:
- For LSPs: binary install path (rustup, npm, brew, etc.)
- For MCPs: how to launch the server (npx command, env vars)
- For skills: when to invoke (frontmatter description)

### Step 6: Validate (REQUIRED — refuse to commit on failure)

```bash

python scripts/validate.py
python scripts/generate_marketplace.py
git diff --exit-code .claude-plugin/marketplace.json

```

All must exit 0. If `pytest` fails, STOP and report — do NOT commit.

### Step 7: Commit

Single atomic commit with conventional-commit format:
- `feat(catalog): add <item-slug> to <plugin-name>` for add-item mode
- `feat(catalog): add <plugin-name> plugin with <item-slug>` for add-plugin mode

## D15 strict hooks ownership check (always)

- If `add-plugin` mode proposes `hooks` in the new plugin's `components` list → REFUSE with a clear error pointing at D15 + the existing `tests/test_plugin_components.py::test_no_plugin_ships_hooks_outside_hooks_plugin` invariant.

# /heretek:refresh-pins

Verify every catalog item is still healthy against the D7 vetting bar. Surfaces stale items (stars dropped, license changed, critical CVE published) for review. Read-only by default — does NOT modify catalog.yaml.

## When to use

- Quarterly cadence (recommended — every 90 days)
- Immediately when a critical CVE is published against a vetted upstream
- Before a release tag to confirm the catalog is fresh

## Steps

```bash
# Activate venv + install deps
cd <heretek-repo>
. .venv/bin/activate
pip install -q -r requirements-dev.txt

# Get a GitHub token (in order of preference):
#   1. Use GITHUB_TOKEN env var if set
#   2. Otherwise use gh CLI auth token
#   3. Otherwise run in offline mode (no API calls)
TOKEN="${GITHUB_TOKEN:-$(gh auth token 2>/dev/null || echo)}"

# Run the refresh-pins tool
python scripts/refresh_pins.py --github-token "$TOKEN"
```

## Reading the output

| Exit | Meaning |
|---|---|
| 0 | All items fresh — no action needed |
| 1 | One or more items stale — review the output table |

The output is a table of `STATUS | PLUGIN | ITEM | DETAIL` rows:
- `ok` — item is current (stars ≥ 500, license matches, no critical CVEs)
- `skipped` — offline mode (no token); only verified stored vetting.date is within staleness window
- `stale_stars` — upstream has < 500 stars (or API error)
- `stale_commit` — stored vetting.date is older than 365 days (or PyYAML date-parsing edge case)
- `license_drift` — upstream license no longer matches catalog
- `cve_alert` — upstream has open critical (CVSS ≥ 9.0) security advisories

For each stale item, decide whether to:
- Bump the catalog `sha:` field to a newer upstream commit (if the item is otherwise healthy)
- Move the item to `catalog/rejected.md` (if upstream is unmaintained or risky)
- Write a follow-up ADR documenting the change

## `--update-shas` mode

---

# /heretek:merge-and-push

After a subagent-driven-development run produces a feature branch with all tasks complete and reviewed, this skill merges it back to main and pushes to origin. Each step has guards that refuse to proceed on common failure modes.

## When to use

- A sub-project branch (e.g. `sp4-aggregation-launch`) has completed all 8 tasks
- The final whole-branch review returned "Ready to merge"
- You've decided to merge locally (alternative: push + create PR via `gh pr create`)

## Pre-flight checks (REQUIRED before any action)

Before doing anything, confirm with the user. Print a one-line confirmation prompt:

> "Merge `<feature-branch>` → `<base-branch>` and push? (y/n)"

Then verify:

1. **Working tree clean**: `git status --porcelain` must be empty. If not, refuse with "Working tree is dirty; commit or stash first."
2. **Not detached HEAD**: `git rev-parse --abbrev-ref HEAD` must return a branch name. If `HEAD`, refuse with "Detached HEAD; cannot merge."
3. **Source branch exists**: the feature branch must be a real ref. If the user passed an invalid branch, refuse.
4. **User confirmed**: print what you're about to do before doing it.

## Steps (only after all pre-flight checks pass)

```bash
# Step 1: checkout base + merge
git checkout main  # or whatever base branch
git pull --ff-only   # skip with warning if upstream gone
git merge <feature-branch> --ff-only

# Step 2: test on merged result — refuse to push if tests fail
. .venv/bin/activate
pytest -q
python scripts/validate.py
python scripts/generate_marketplace.py
git diff --exit-code .claude-plugin/marketplace.json
bash tests/smoke/fast_gate_smoke.sh

# Step 3: push — only after all tests pass
git push -u origin main

# Step 4: cleanup — only after push succeeds
git worktree remove <worktree-path>     # only if worktree exists
git branch -d <feature-branch>
```

## Hard guards

- **Dirty tree** → STOP, refuse to proceed. User must commit or stash first.
- **Detached HEAD** → STOP. The skill cannot determine a source branch to merge.
- **Merge not fast-forwardable** → STOP. Suggest `git merge --no-ff` or rebase the feature branch first.
- **Any test fails on merged result** → STOP. Do NOT push. Do NOT cleanup. User must investigate.
- **Push fails (network, auth, conflict with remote)** → STOP. Do NOT cleanup. User must investigate.
- **Worktree removal fails** → WARN, don't fail. Branch deletion is the critical step.

## Acceptance criteria

- [ ] User confirmed before any destructive action
- [ ] Working tree was clean before merge
- [ ] Merge was fast-forward (or user explicitly chose --no-ff)
- [ ] All tests passed on merged result
- [ ] Push succeeded before cleanup
- [ ] Worktree removed (if it existed)
- [ ] Feature branch deleted locally (NOT pushed-deleted — just local `git branch -d`)

## Out of scope

- Auto-creating PRs (use `gh pr create` separately)
- Cross-repository coordination (heretek has one repo)
- Resolving merge conflicts (the skill refuses and asks the user to rebase first)
- Updating issue trackers or release notes
